# Desktop and CLI internals

Verified facts the tool rests on. Do not re-derive them; cite them. Evidence labels: **M** measured on a Mac or in cloned source, **O** official Anthropic doc, **R** reported (issue, README, blog), **U** unverified or inferred. Measured 2026-10-23 against Desktop 3.6556.2 and CLI 2.1.309 (Desktop bundled Claude Code 2.1.304 and 2.1.308) unless a sentence names a later date or version (the 2026-10-26 Keychain and 2.1.310 binary facts below); re-measure after an app update before trusting a layout claim. Re-measured 2026-10-28 on Desktop 4.29.0: the folder, key, cookie, `config.json` format and process-environment claims below still hold, with the differences each sentence dated 2026-10-28 names. The full digest is `docs/research.md`.

## Desktop paths and keys

- App support folder `~/Library/Application Support/Claude/` (M). `config.json` holds the login in three keys, `oauth:tokenCache`, `oauth:tokenCacheV2`, `lastKnownAccountUuid`; one login at a time (M). The app writes it tab-indented, no final newline, mode 0600 (M; `jq_write` matches that). Cookies are `Cookies` and `Cookies-journal`, in `Network/` when that folder exists (M).
- `config.json.journal` is the app's write-ahead copy, headed by the sha256 of the `config.json` it came from; the app discards it at startup when the digest no longer matches, as after a switch (M). Leave it alone.
- The token caches and cookies are encrypted with the "Claude Safe Storage" login-Keychain password, Chromium style: PBKDF2-SHA1 of that password, salt `saltysalt`, 1003 rounds, 16 bytes, as an AES-128-CBC key, IV of 16 spaces, `v10` prefix on the ciphertext (R for the scheme, Chromium's macOS os_crypt; M only that the self-check round-trips a fixture the same way; `usage` printing figures on a real Mac is what confirms it against a real cache). Per Mac, so profiles don't transfer between Macs.
- Reading that Keychain item prompts; using `/usr/bin/security` makes the user's "Always Allow" persist (M in CCSwitcher's source and the Raycast usage command). At most one call per 5 minutes: claude-swap issue 496 reported that about eight `security` spawns a second crashed securityd (fixed in its v0.28.0 by PR 498, which caches the read and backs off 60 s after a failure; closed 2026-10-26), so the menu bar app's usage poll makes one call per run and never runs faster than that.
- Desktop signs in with its own OAuth flow and ignores `ANTHROPIC_API_KEY`, `apiKeyHelper` and CLI profiles (O). Whether it honours `CLAUDE_CONFIG_DIR` is U.
- Other files beside the login (M): `claude_desktop_config.json` (local MCP servers; survival across sign-out is U), `ccd-session-presets.json` keyed `byAccount`, `local-agent-mode-sessions/<account>/<org>/spaces.json` (Desktop projects; its `projects` and `migration` keys are org-bound) and `scheduled-tasks.json`, plus a per-org `archived-sessions.idx` and `scheduled-tasks.json` beside the session pointers. On 4.29.0 (M, 2026-10-28) the top-level `scheduled-tasks.json` and every `spaces.json` are gone: `local-agent-mode-sessions/<account>/<org>/` holds a `scheduled-tasks.json` (keys `scheduledTasks`, `recordedSkips` and two boundary stamps) and a `skills-plugin/` folder sits beside the account folders. None of these is synced yet.

## Code tab session index

- `claude-code-sessions/<accountUuid>/<orgUuid>/local_<uuid>.json`, one per session (M layout, undocumented). Keys: `cliSessionId`, `cwd`, `title`, timestamps including `lastActivityAt`, `isArchived`, `permissionMode`, `model`, `effort`, `remoteMcpServersConfig`. No account or org field inside, so a plain copy between folders works (M). On 4.29.0 a pointer carries about 36 keys every session shares (those above among them, plus `sessionId`, `createdAt`, `originCwd`, `titleSource`, turn and remote-control state) and a tail of optional ones (`branch`, `prs`, `writtenBranches`, `spawnedFrom`); 50 pointers read 2026-10-28 still had no account or org key (M).
- `deleted_<uuid>` tombstones sit beside the pointers (R). Sync honours them and never copies a tombstoned id back.
- Switching account or org makes Desktop read a different folder, so the sidebar empties while transcripts stay (R, issue 74662, open since 2026-07-06). Symlinking the folder fails with "Refusing non-directory at private dir path" (R). Never touch a record a running Desktop session owns (R).
- Transcripts are shared: `~/.claude/projects/<cwd-slug>/<session-id>.jsonl`, written by the CLI and the Code tab alike (M, O). Every 2.1.30x transcript carries a `credential_org` attachment with `organizationUuid` (M); whether resume compares it to the active account is U. CLI retention is `cleanupPeriodDays` (default 30); Desktop transcripts stay unless `desktopSessionCleanupPeriodDays` is set (O).

## Code tab process environment

- Each Desktop-spawned `claude` has `CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_CODE_ACCOUNT_UUID`, `CLAUDE_CODE_ORGANIZATION_UUID`, `CLAUDE_CODE_USER_EMAIL`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_SDK_HAS_HOST_AUTH_REFRESH` and a `--settings` flag (M, `ps -E`, names only; the four Code-tab session processes alive on 2026-10-28 under 4.29.0 all carried them, plus `CLAUDE_CODE_SDK_HAS_OAUTH_REFRESH`, `CLAUDE_CODE_SUBSCRIPTION_TYPE` and `CLAUDE_CODE_RATE_LIMIT_TIER`). The MCP servers and hooks a session spawns inherit `CLAUDE_CODE_ENTRYPOINT`, the account and org uuids and the email, but not the token, so a `ps` match on the entrypoint overcounts sessions about twelve to one (M, 2026-10-28).
- `CLAUDE_CODE_OAUTH_TOKEN` outranks the Keychain login (O precedence: cloud-provider vars, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY`, `apiKeyHelper`, `CLAUDE_CODE_OAUTH_TOKEN`, an Anthropic profile or federation credential when one is named, then `/login`). So a terminal `/login` or a Keychain swap never moves a Code-tab session; only changing Desktop's own sign-in does. The host app refreshes the token itself.
- Plugin SessionStart hooks and plugin MCP tools run in Code-tab sessions (M).

## CLI credentials

- Keychain generic password service `Claude Code-credentials`, fallback `~/.claude/.credentials.json` mode 0600 (O). The JSON holds `claudeAiOauth` with `accessToken`, `refreshToken`, `expiresAt`, `scopes`, `subscriptionType` (M in tool sources). The identity block `oauthAccount` in `~/.claude.json` pins the org per request, so a token swap without it can bill the wrong org (R, two tools agree).
- Per-directory item `Claude Code-credentials-<first 8 hex of sha256(NFC(CLAUDE_CONFIG_DIR))>` (R). The CLI reads the Keychain before the file (M in source) and caches the read 30 s (M in the 2.1.310 binary, `sKt=30000`); its storage reads, writes and deletes give `security` 2 s, and only the startup prefetch 10 s, so a Keychain prompt open past 2 s reads as signed out for that process (M). The locks are directories, `mkdir` to take, stale after a threshold: `~/.claude/.oauth_refresh.lock` (60 s), `~/.claude.lock` (60 s) and `~/.claude.json.lock` (10 s) (M in claude-swap source). Since 2.1.310 the CLI also writes `.oauth_refresh.lock.owner` (pid, process start, lock birthtime) and takes over a dead holder's locks early only when that record exists; a record-less dir, the tool's, is judged by mtime staleness alone (M). Its config writer retries `~/.claude.json.lock` at 200, 400, 800, 1600, 3200 and 4000 ms, then takes over a dir older than 10 s; its token refresh tries the credential locks 5 times, 1 to 2 s apart, then fails that attempt (M). Config writes diff against the last read and write only changed keys, and refuse when the re-read file lacks auth the cache has (GH #3117) (M); that a running `claude` therefore leaves a spliced `oauthAccount` alone is inferred, not reproduced (U).
- Measured 2026-10-26 on this Mac: the live item is 14625 bytes, 14053 of them `mcpOAuth`, so a `security -i` line (4019 bytes at most) cannot carry it. `find-generic-password -w` prints a value with any non-ASCII byte as one hex string (M, a UTF-8 test item), so the tool decodes an all-hex read.
- Claude Code 2.1.310 (read from its binary) reads its item with `security find-generic-password -a <user> -w -s <service>` and writes it with an `add-generic-password -U -a "<user>" -s "<service>" -X "<hex>" ` line on `security -i` stdin when that line is at most 4032 bytes, else with `security add-generic-password -U -a <user> -s <service> -X <hex>` on argv (it logs "Keychain payload exceeds security -i stdin limit; using argv") (M). That is the tool's route since 0.3.3: `security -i` keeps at most 4019 bytes of a line and corrupts the rest, its parser rejects the shell's `'\''` escape (exit 45), `-X <hex>` round-trips any value, the `-w` prompt reads the terminal rather than a pipe, exit 44 means absent (M), and exit 36 with an item the CLI knows exists means the keychain is locked and the failure transient (M).
- A Keychain item carries a partition_id ACL entry beside the application ACL: `/usr/bin/security` is in partition `apple-tool:`, the Command Line Tools python is in `apple:`. An app in the application ACL still prompts (with the login password) unless its partition is in the item's partition list, the GUI's Always Allow edits only the application ACL, and an in-place update resets the partition list to the writer's partition (M, corroborated by anthropics/claude-code issue 62361). So the tool goes through `security` only, in Claude Code's shape.
- The item's account is the macOS user name and `oauthAccount.accountUuid` in `~/.claude.json` equals Desktop's `lastKnownAccountUuid` for the same claude.ai account (M). `claude auth status` prints JSON by default with `orgId` and `email` (M). `~/.claude.json` is 2-space indented, mode 600 (M).
- The item's other top-level keys (`mcpOAuth`, `mcpOAuthClientConfig`, `mcpXaaIdp`, `mcpXaaIdpConfig`, `pluginSecrets`) are shared across accounts (M). `trustedDeviceEnrolledAfterRefusalAtMs` is written beside `trustedDeviceToken` and is account-scoped (M).
- `CLAUDE_SECURESTORAGE_CONFIG_DIR`, when defined and non-empty, selects the suffixed item and the `.credentials.json` path instead of `CLAUDE_CONFIG_DIR`; defined and empty selects the default item; Desktop-spawned child sessions carry it (M, names from `ps -E`; on 2026-10-28 under 4.29.0 only one `sdk-py` child carried it, and none of the four Code-tab session processes did).
- `CLAUDE_CONFIG_DIR` gives its own settings, history, login and Keychain entry; `claude --resume <id>` searches only the current config dir, so per-account config dirs split history (O).
- Rate limits auto-continue since v2.1.234; the Code tab has its own "Auto-continue when limits reset" checkbox. The prompt cache is per account, so the first turn after a switch re-sends the transcript (R).

## Plans and usage limits

Measured 2026-10-30 against Desktop 4.4212.0, Claude Code 2.1.309 and 2.1.314, and live responses for two Ultra orgs (`private/probe-usage.sh`, `private/probe-profile.sh`).

- On 2026-10-30 Max 5x became Max and Max 20x became Ultra; verified Ultra accounts have no 5-hour limit, newer ones keep a temporary one until verified, weekly limits are unchanged, and Max and Ultra have a separate weekly limit for Fable (O, support articles 11145838 and 11049741, claude.com/pricing).
- The plan name is server-sent: `GET https://api.anthropic.com/api/oauth/profile` with the bearer token answers `organization.plan_display_name` (`Ultra`) and `plan_display_label` (`Ultra plan`) over an unchanged `organization_type` (`claude_max`) and `rate_limit_tier` (`default_claude_max_20x`). Desktop and the CLI both call it; neither bundle has an `Ultra` plan literal (M). No profile field marks the verified state: a verified and an unverified Ultra org answered the same body (M).
- `GET /api/oauth/usage` keeps `five_hour` and `seven_day` and adds a `limits` list (`kind` `session`, `weekly_all`, `weekly_scoped`; `percent`, `severity`, `resets_at`, `scope.model.display_name`, `is_active`; a `scope.surface.display_name`, which Desktop's parser also reads, is U), `extra_usage`, `spend`, `seven_day_breakdown` and many null codename keys (M). A verified Ultra answers `five_hour` as `{"utilization":0.0,"resets_at":null}`; the unverified one had a real window (M). The Fable limit is only in `limits` as `weekly_scoped`; at 100% the named windows still carry `locked_reason: null` (M). `is_active` marks the limit that binds first, not an enforced one (M). Desktop's own parser reads `limits[kind == weekly_scoped]` into "Weekly · <display_name>" rows (M, app.asar).
- Desktop keeps `plan-usage-history.json` beside `config.json`: `{version: 2, samples: [{t, org, u: {fh, sd, ...}}]}`, 30 days, one sample per org per 4.5 minutes at most (M). Not read by the tool.

## Counting tool runs

- A bash fork keeps its parent's argv, so `ps` and `pgrep -f` list every subshell and command substitution as another `claude-multipass ...` row: one run of a script that backgrounds three subshells, each with a `$(...)`, showed 7 rows (M, 2026-10-28). `usage` backgrounds one subshell per profile, so a `ps` count of `usage --json` is not a run count. Count a side effect that happens once per run instead: one `security` call per `usage` run. A `ps` poll cannot see it either, since a `security` process lives about 10 ms (M, 2026-10-28); a pass-through `security` in `~/.local/bin`, which the app's runner puts ahead of `/usr/bin`, logging the subcommand and `-s` service and exec'ing the real binary, counts exactly. Measured that way on 2026-10-28 with 0.5.1: one Safe Storage read on relaunch and one per Refresh click, nine seconds apart, so the app runs `usage` once per poll and the earlier figure of about 40 was the subshell overcount (M).
